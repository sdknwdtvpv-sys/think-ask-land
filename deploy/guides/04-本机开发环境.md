## 一、一次性准备（只做一次）

### 1.1 Node 必须是 22 —— 这条最要命

**症状**：`bash .build/run-all.sh` 里几乎所有套件都红，报 `ERR_REQUIRE_ESM` 或者 `require() of ES Module ... not supported`。
看着像"整个项目坏了"，其实只是 node 版本不对。

**根因**：jsdom 30 的 `engines` 写的是 `^22.22.2 || ^24.15.0 || >=26`。
这台机器默认 PATH 上是 **nvm 的 v18.20.8**，`require("jsdom")` 直接抛错。
注意：本机还装了 **v20.20.2，同样不满足**（engines 要求 22.22.2 起），别用。

**现在的处理**：仓库里加了一个 `.nvmrc`（内容 `22`），并且 `.build/run-all.sh` 会**自己挑一个满足要求的 node**：

```
HZ_NODE（显式指定） > PATH 里的 node（满足要求才用） > ~/.nvm/versions/node/*/bin/node > /usr/local/bin > /opt/homebrew/bin
```

所以**默认 PATH 上是 v18 也能跑**，脚本会自动把 v22.23.2 插到前面。
如果一个都找不到，它会打印中文指引并退出 1，而不是丢一堆英文报错。

```bash
# 确认现在会用到哪个 node
bash .build/run-all.sh smoke          # 能输出「通过 34 / 34」就说明 node 挑对了

# 想显式指定（一般不需要）
HZ_NODE="$HOME/.nvm/versions/node/v22.23.2/bin/node" bash .build/run-all.sh
```

### 1.3 ⚠️ 本机 npm 缓存是坏的 —— 所有 npm 命令都要加 `--cache`

**症状**：任何 `npm install` / `npm view` 都直接失败，报

```
npm error code EPERM
npm error syscall open
npm error path /Users/elliot/.npm/_cacache/tmp/xxxx
npm error Your cache folder contains root-owned files…
```

**根因**：`/Users/elliot/.npm` 里有 root 所有的文件（npm 旧版本的已知问题）。
**这不是网络问题** —— 网络是通的（`registry.npmjs.org` 直连返回 200）。

**修法：把缓存指到工作区内**（`.gitignore` 里早就预留了 `.build/.npmcache/`，原作者就是这么绕的）：

```bash
cd /Users/elliot/Harness/think-ask-land
npm install --cache .build/.npmcache          # 装 App 依赖（Capacitor 等）
npm view @capacitor/core version --cache .build/.npmcache   # 查询也要加
```

> 想彻底修掉的话需要 `sudo chown -R 501:20 /Users/elliot/.npm`（要管理员密码）；
> 不修也行，加 `--cache` 就完全够用。
>
> 另外本机 npm registry 指向 `registry.npmmirror.com`（国内镜像），这是**好事**，不用改。

### 1.4 iOS 原生工程怎么构建（Capacitor 壳）

> 这一节对应 APP-PLAN.md 的 Phase 1。工程已经在 `ios/` 下了。

```bash
npm run sync:web        # 组装 www/（改了网页代码后必须先跑）
npm run cap:sync        # 把 www/ 同步进 ios/ 并更新插件
npm run cap:open        # 用 Xcode 打开（推荐：签名与真机都在 Xcode 里做）
```

**CocoaPods 不需要装** —— Capacitor 8 起 iOS 走 **SPM**，
生成出来的 `ios/App/CapApp-SPM/Package.swift` 里 5 个插件全是本地 path 包。

⚠️ **首次构建需要 GitHub 可达**：SPM 要拉 `capacitor-swift-pm`（精确锁 8.5.2）
以及 `@capacitor/filesystem` 传递依赖的 `ion-ios-filesystem` 等仓库。

**本机实测：`git` 到 `github.com:443` 是间歇性的**（`curl https://github.com` 能通但很慢，
`git ls-remote` 有时直接 75 秒超时）。所以命令行 `xcodebuild` 可能卡在 `Resolve Package Graph`
并报 `Could not resolve package dependencies`。**这不是工程有问题 —— 重试即可**（本机第二次就成功解析并构建通过了）。

**已经验证过的完整链路**（本机实测）：

```bash
npm run sync:web     # 组装 www/
npm run cap:sync     # 同步进 ios/ —— 5 个插件全部走 SPM
cd ios/App && xcodebuild -project App.xcodeproj -scheme App \
  -sdk iphonesimulator -configuration Debug \
  -destination 'generic/platform=iOS Simulator' build      # → BUILD SUCCEEDED
xcrun simctl boot "iPhone 17"
xcrun simctl install booted <上面产出的 App.app>
xcrun simctl launch booted work.elliotli.siwendao
xcrun simctl io booted screenshot /tmp/shot.png            # 确认真的渲染出来
```

真机构建与签名仍建议用 `npm run cap:open` 在 Xcode 里做（需要开发者账号）。

## 四、两个真实问题的根因（症状 → 根因 → 谁守着）

### 4.1 `gen-guard-test` 4/5 —— 生成器"全失败"时仍在磁盘上留东西

**症状**（干净检出上必然出现）：

```
❌ 失败的那次运行不能破坏已有音频  —— 索引条目数变了:{"a":-1,"b":-1} → {"a":0,"b":-1}
```

**复现**（不需要任何密钥）：

```bash
cd /Users/elliot/Harness/think-ask-land
rm -rf audio
node .build/gen-guard-test.js      # → 通过 4 / 5,并留下 audio/
find audio -type f                 # → config.json、tc-502007/index.json、tc-502007/meta.json
```

**根因**：这个套件用**假密钥**跑真实的 `.build/gen-audio.py`（预期鉴权失败 AuthFailure）。
一条都没生成成功，但生成器仍然无条件地写了：

| 位置 | 写什么 |
|---|---|
| `gen-audio.py:611-612` | `os.makedirs(audio/<音色>/{p,z,w,s})` |
| `gen-audio.py:657-668` | `audio/<音色>/index.json` = `{}` |
| `gen-audio.py:670` | `audio/<音色>/meta.json` |
| `gen-audio.py:722` | `audio/config.json` = `{"default":"","roles":{},"voices":{}}` |

生成器在**别的地方**是记得"没产出就别登记"的（`gen-audio.py:698` 明确判了 `count > 0`，`:714` 还会把空音色从注册表里摘掉），
但**磁盘上的文件**没做同样的判断 —— 于是守卫测试的断言抓得完全正确。

**为什么这台机器上才炸**：一旦污染已经存在，`idxCount` 从 `-1`（文件不存在）变成 `0`（空索引），
再跑一次 `before` 就已经是 `0` 了，数字"不变"，于是 **5/5 通过**。
换句话说这是一个**只有新克隆/干净机才会暴露**的 bug。

**连带伤害**：它顺手写出的空 `audio/config.json` 会把 `voice-config-test` 带崩（见 4.2）。

### 4.2 `voice-config-test` 崩溃 —— 它需要真实的音频包

**症状**：

```
TypeError: Cannot read properties of undefined (reading 'key')
    at .build/voice-config-test.js:150
```

**根因（两层）**：

1. `voice-config-test.js:39` **无条件**读 `audio/config.json`。这个文件不进版本库，
   干净检出上本来不存在（本机之所以存在，是 4.1 的 bug 顺手写出来的**空**配置）。
2. 配置是空的 → `AP.voiceList()` 里没有任何音色 → `.filter(v => v.current)[0]` 是 `undefined`
   → 取 `.key` 就抛 TypeError。

**要真正跑通它**，必须先有真实音频包（761 字 → **每条音色 3052 条**：单字 759 / 组词 1522 / 例句 761），
也就是先走一遍 `01-tencent-key-and-audio.md`（需要腾讯云密钥）。
原开发机上是绿的，就是因为那边 `audio/` 早就生成好了。

> 顺带：`01` 号指南里写的 `1533/1533` 是**旧数字**（字库从 316 涨到 761 字），现在应为 `3052`。

### 4.3 为什么这套测试"只能在原开发机上全绿"

把 4.1 和 4.2 放在一起看，`gen-guard-test` 里其实有**两条互相牵制的断言**：

- 第 3 条：**失败的那次运行不能破坏已有音频**（→ 要求失败时别写文件）
- 第 5 条：失败之后 `--list` **必须退出码 0**（`gen-guard-test.js:91`）

而 `--list` 在 `audio/config.json` 不存在时是 `sys.exit(...)`，**退出码 1**（`gen-audio.py:460`）。
在干净机器上，这两条只能靠"失败时写出一个空 `config.json`"同时满足 ——
**测试之所以全绿，恰恰是因为那个 bug 在替它兜底**。
这正是它能潜伏到现在的原因。

**修的话**（本次按你的决定**未改**，留档备查）：生成器在"本次零产出且此前没有索引"时不写任何文件，
同时让 `--list` 在没有 `config.json` 时打印"还没有生成任何音色"并退出 0（`--list` 是只读查询，不该算失败）。
